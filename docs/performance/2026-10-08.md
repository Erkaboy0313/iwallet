# Performance investigation ? 2026-10-08

Deployed release: `20261008-performance-1` on `track.hygen.uz`.

## Findings

The server was not resource-starved: the web container used about 2% CPU and
146 MiB RAM during the initial sample. There was one user and no transactions.
Server-side history and debt rendering took roughly 6?14 ms after warm-up;
weekly reports took 18?21 ms. Home had 25 SQL queries and took about 85?107 ms
when warm. That was not enough to explain multi-second page navigation.

The browser waterfall identified the main avoidable delays:

1. CSS and JavaScript URLs included the current Unix timestamp. Each new page
   generated different URLs and downloaded about 43 KB of compressed assets
   again, even though their contents had not changed.
2. Telegram's external SDK was a parser-blocking script. In the baseline cold
   navigation that request took about 1.5 seconds. It prevented the browser
   from parsing the body while it loaded.
3. Every home visit rendered a skeleton, loaded JavaScript, then fetched
   `/app/home/content/`, even when the session already identified the user.
4. Home could synchronously call CBU for missing rates, with up to five attempts
   and backoff. This was a latent delay, not the active cause in this sample:
   production already had today's rates during profiling.

## Changes

- Production assets now use Django's content-hashed static storage and immutable
  cache headers. Timestamp query parameters were removed from all affected
  templates. Tailwind's source-only `css/app.css` is excluded from collectstatic.
- The Telegram SDK loads asynchronously. Its ready/expand bootstrap works both
  before and after SDK completion. Signed launch data is read from the URL
  fragment without double-decoding while the SDK is pending.
- A valid returning user's home renders its balance in the initial response.
  Anonymous first launches retain the existing authenticated htmx bootstrap.
- Page rendering reads stored exchange rates only. An hourly systemd timer runs
  `fetch_rates` independently of page requests.
- Re-reading an unchanged authenticated session no longer forces a session write.

Django documents content hashing in
[ManifestStaticFilesStorage](https://docs.djangoproject.com/en/5.2/ref/contrib/staticfiles/#manifeststaticfilesstorage).
Telegram's SDK integration is documented in
[Initializing Mini Apps](https://core.telegram.org/bots/webapps#initializing-mini-apps).

## Browser measurements

Chrome headless, 390?844 mobile viewport, authenticated diagnostic session,
HTTPS from the same local workstation to production. Each run used a fresh
browser context, then visited the following routes sequentially. Browser cache
was enabled. These are individual diagnostic samples, not a load test or an
SLA; network/TLS conditions affect the cold request. This measures Chrome page
content, not Telegram's native launch spinner or a phone on cellular data.

The baseline waited for load plus home content. The new run records DOM-ready
plus home content, without waiting for the now-independent Telegram SDK.
This matches when the app becomes usable. For the cold home, first contentful
paint was 2712 ms before and 1532 ms after; actual rendered home content in the
baseline arrived later, after its second HTTP request.

| Route (in visit order) | Before | After |
|---|---:|---:|
| `/app/home/` | 3463 ms | 1423 ms |
| `/app/transactions/history/` | 1436 ms | 245 ms |
| `/app/debts/` | 3593 ms | 192 ms |
| `/app/reports/weekly/` | 1482 ms | 220 ms |
| `/app/home/` | 1337 ms | 305 ms |
| `/app/transactions/history/` | 974 ms | 194 ms |

Warm-navigation median: **1436 ms ? 220 ms** (about 6.5? faster in these samples).
All four local CSS/JS resources transferred **0 bytes** on warm navigations after
the change. They previously transferred about 43 KB each navigation. Returning
home issued **zero** `/app/home/content/` requests after the fix.

The home view still has 23 SQL queries and took roughly 72?113 ms after warm-up
in the second server-side profile. No financial aggregation logic was changed.
There is room to consolidate queries if later data-volume measurements justify
it, but the measured multi-second problem was primarily the browser load path.

## Validation

- 638 pytest tests passed, including returning-session rendering, user-data
  isolation, deleted-session fallback and no CBU calls on page rendering.
- Ruff, modified-template lint/format checks, production collectstatic,
  `nginx -t` and Django's production checks passed.
- A real browser test held the Telegram SDK response pending: both an existing
  session and a first launch with signed initData containing `+`, `%` and `&`
  authenticated and rendered before the SDK loaded. Late SDK ready/expand ran.
- Navigation through all main tabs had no JavaScript errors.
- Production hashed assets returned 200 with immutable cache headers. All four
  IWALLET containers were healthy; the rates timer completed successfully.
